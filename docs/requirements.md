# Спецификация требований

## 1. Постановка задачи

Обращения сотрудников в техническую поддержку поступают из разных каналов. При ручном учёте возможны потеря обращений, отсутствие контроля сроков и ошибки при подготовке статистики. Необходимо единое REST API, позволяющее фиксировать, обрабатывать и анализировать заявки.

**Целевая аудитория:** сотрудники, создающие обращения; специалисты технической поддержки, обрабатывающие заявки; руководитель службы, анализирующий показатели.

**Границы проекта:** серверное приложение Java + Kotlin, PostgreSQL, Swagger/OpenAPI, Docker Compose и CI/CD. Веб-интерфейс, авторизация пользователей, уведомления, микросервисы и Kubernetes не входят в обязательный объём.

## 2. Пользовательские истории и критерии приёмки

| ID | История | Проверяемый критерий приёмки |
|---|---|---|
| US-01 | Как сотрудник, хочу зарегистрировать заявку, чтобы обращение не потерялось | `POST /api/tickets` с заголовком, категорией и корректным приоритетом возвращает HTTP 201; статус созданной заявки — `NEW` |
| US-02 | Как специалист, хочу видеть заявку по идентификатору | `GET /api/tickets/{id}` возвращает заявку; неизвестный ID — HTTP 404 |
| US-03 | Как специалист, хочу уточнять описание, приоритет и срок | `PATCH /api/tickets/{id}` изменяет эти поля у открытой заявки; у завершённой или отменённой — HTTP 409 |
| US-04 | Как специалист, хочу переводить заявку между статусами | Допускаются `NEW → IN_PROGRESS → RESOLVED` и отмена из `NEW`/`IN_PROGRESS`; запрещённый переход — HTTP 409 |
| US-05 | Как руководитель, хочу видеть историю обработки заявки | После изменения статуса `GET /api/tickets/{id}/history` содержит переходы по времени; неуспешная операция не создаёт запись |
| US-06 | Как специалист, хочу фильтровать заявки | `GET /api/tickets` поддерживает фильтрацию по статусу, приоритету, категории, датам и пагинацию |
| US-07 | Как руководитель, хочу получать статистику за период | `GET /api/reports/summary` агрегирует только заявки, созданные в `[from, to)`, и возвращает показатели по ТЗ |
| US-08 | Как администратор, хочу восстановить данные после сбоя | После перезапуска контейнеров заявки остаются; SQL-копия восстанавливается в отдельную тестовую базу |

## 3. Функциональные требования

**FR-01.** Создание заявки: заголовок и категория обязательны, приоритет — `LOW`/`MEDIUM`/`HIGH`, начальный статус `NEW`.

**FR-02.** Чтение заявки по ID и списка с фильтрацией, поиском и пагинацией.

**FR-03.** Изменение описания, приоритета и срока открытой заявки.

**FR-04.** Изменение статуса только по допустимым переходам. Закрытые и отменённые заявки повторно не открываются.

**FR-05.** Статус и запись истории сохраняются в одной транзакции.

**FR-06.** Ошибки: HTTP 400 для невалидного ввода, 404 при отсутствии заявки, 409 для запрещённой операции.

**FR-07.** Сводка за `[from, to)`: количество созданных заявок, распределение статусов/приоритетов, число открытых просроченных, среднее время решения только `RESOLVED`, `null` при отсутствии решённых.

**FR-08.** Справочник категорий предоставляется через REST API.

## 4. Нефункциональные требования

| ID | Требование | Способ проверки |
|---|---|---|
| NFR-01 | Воспроизводимый запуск из репозитория | `docker compose up -d --build`, проверка health/API |
| NFR-02 | Сохранность данных | Повторный GET после `docker compose restart` |
| NFR-03 | Отсутствие секретов в Git | Проверка `.gitignore`, `.env.example`, GitHub Secrets |
| NFR-04 | Единая структура ошибок | Проверка ответов HTTP 400/404/409 (текстовые поля требуют отдельной проверки реализации) |
| NFR-05 | Автоматические тесты и покрытие | Gradle, JUnit, Testcontainers, JaCoCo |
| NFR-06 | Диагностируемость | Логи stdout/stderr, `/actuator/health` |
| NFR-07 | Переносимость | Docker-образ для AMD64 и ARM64 |

## 5. Контракт API

Точные JSON-схемы, параметры и HTTP-ответы описаны в [`openapi.json`](openapi.json). Примеры выполнения запросов доступны в Swagger UI после запуска приложения.

## 6. Правила просрочки

Заявка просрочена, если `dueAt` меньше текущего времени и статус `NEW` либо `IN_PROGRESS`. Момент равенства времени сроку нужно проверять отдельно как граничный случай.
