## 1. Цель и задачи практики

Целью учебной практики является освоение полного цикла разработки серверного приложения: от анализа требований и проектирования архитектуры до реализации, тестирования, контейнеризации и автоматизированного развёртывания.

В рамках практики разработан сервис Support Service - REST API для регистрации и обработки заявок на техническую поддержку.

Основные задачи проекта:

- Разработать серверное приложение на Java и Spring Boot.
- Реализовать управление заявками, категориями и статусами.
- Организовать хранение данных в PostgreSQL.
- Обеспечить автоматическое применение миграций базы данных.
- Реализовать модуль статистики на Kotlin.
- Разработать модульные и интеграционные тесты.
- Подготовить контейнеризированную среду запуска.
- Настроить автоматическую сборку, тестирование и развёртывание.
- Проверить резервное копирование, восстановление данных и откат приложения.
- Подготовить техническую документацию.

## 3. Реализация основного функционала на Java

На Java реализован REST API управления заявками технической поддержки.

### Основные возможности

1. Создание заявки с указанием заголовка, описания, категории, приоритета и срока выполнения.
2. Получение заявки по идентификатору.
3. Просмотр списка заявок с фильтрацией и пагинацией.
4. Редактирование открытых заявок.
5. Изменение статусов в соответствии с установленными правилами.
6. Получение истории изменения статусов.
7. Получение справочника категорий.
8. Валидация запросов и обработка ошибок.

### Бизнес-правила

При создании заявке присваивается статус `NEW`.

Поддерживаются следующие переходы:

- `NEW → IN_PROGRESS`
- `IN_PROGRESS → RESOLVED`
- `NEW → CANCELLED`
- `IN_PROGRESS → CANCELLED`

Завершённые и отменённые заявки нельзя редактировать или повторно открывать.

Для запрещённых переходов возвращается HTTP 409 Conflict.

При обращении к несуществующей заявке возвращается HTTP 404 Not Found.

Некорректные входные данные обрабатываются с использованием механизмов валидации Spring Boot.

Изменение статуса и сохранение записи в истории выполняются в рамках одной транзакции.

### Работа с базой данных

Для хранения информации используется PostgreSQL 16.

Реализованы таблицы:

- `tickets` - заявки;
- `categories` - категории;
- `ticket_status_history` - история изменения статусов.

Для управления структурой базы данных применяется Flyway.

Миграции позволяют автоматически создавать необходимую схему при запуске приложения.

## 4. Интеграция Kotlin

На Kotlin реализован модуль формирования статистики по заявкам.

Основной метод:

`GET /api/reports/summary`

Метод принимает временной интервал и возвращает:

- Количество созданных заявок.
- Распределение по статусам.
- Распределение по приоритетам.
- Количество просроченных открытых заявок.
- Среднее время решения завершённых заявок.

Для расчётов используются заявки, созданные в полуоткрытом интервале `[from, to)`.

### Особенности реализации на Kotlin

**1. Использование nullable-типов**

Среднее время решения может отсутствовать, если в выбранном периоде нет завершённых заявок.

Для корректного представления такого результата применяется nullable-тип.

При отсутствии подходящих данных возвращается `null`, а не некорректное числовое значение.

Безопасная обработка отсутствующих значений также используется при проверке сроков выполнения заявок.

**2. Использование операций над коллекциями**

Для формирования статистики применяются возможности стандартной библиотеки Kotlin:

- `filter` - выбор завершённых заявок;
- `count` - подсчёт просроченных заявок;
- `groupingBy` и `eachCount` - распределение по статусам и приоритетам;
- `mapNotNull` - обработка результатов, для которых доступны необходимые значения;
- `average` - вычисление среднего времени решения.

Использование этих операций позволяет реализовать статистические расчёты без дополнительных циклов и промежуточных структур данных.

### Взаимодействие Java и Kotlin

Модуль статистики работает в составе общего Spring Boot-приложения.

Java-компоненты приложения взаимодействуют с Kotlin-сервисом через механизм внедрения зависимостей Spring.

Kotlin-сервис получает данные с использованием Java-интерфейса репозитория Spring Data JPA.

Таким образом, Java и Kotlin используются совместно в одном приложении и участвуют в выполнении реальных бизнес-функций.

## 6. Обнаружение и исправление дефектов

В ходе тестирования обнаружен дефект BUG-001.

**BUG-001 - потеря срока выполнения при частичном обновлении заявки.**

При отправке PATCH-запроса без поля `dueAt` ранее установленный срок выполнения сбрасывался в `null`.

### Причина

В методе `TicketService.updateTicket()` выполнялось безусловное присваивание значения `request.getDueAt()`.

Если поле отсутствовало в запросе, его значение в объекте запроса было равно `null`.

### Исправление

В `UpdateTicketRequest` добавлены признаки присутствия необязательных полей.

Логика редактирования изменена таким образом, чтобы обновлять поле только при его передаче в запросе.

При этом сохранена возможность явного удаления срока выполнения.

### Проверка исправления

Для подтверждения исправления реализованы:

- Модульный тест `testUpdatePreservesDueAtWhenOmitted`.
- Интеграционный тест `testPatchPreservesDueAtWhenOmitted`.

До исправления модульный тест воспроизводил ошибку.

После исправления оба регрессионных теста и полный набор автоматизированных проверок завершились успешно.

Дефект устранён.

## 7. Контейнеризация и эксплуатация

Для воспроизводимого запуска приложения применяется Docker.

Подготовлены:

- Многоэтапный `Dockerfile`.
- `compose.yaml` для локального запуска.
- `compose.deploy.yaml` для запуска опубликованного образа.
- `.env.example` для настройки переменных окружения.

Docker Compose запускает приложение и PostgreSQL в отдельных контейнерах.

Для сохранения данных используется постоянный Docker volume.

После запуска приложения миграции Flyway применяются автоматически.

Работоспособность контролируется через Spring Boot Actuator.

Основной endpoint проверки состояния:

`GET /actuator/health`

### Проверка сохранности данных

Проверена сохранность заявки после перезапуска контейнеров Docker Compose.

Данные PostgreSQL сохраняются в постоянном томе и остаются доступными после повторного запуска приложения.

Резервная копия восстановлена в отдельную базу `supportdb_restore_test`.

## 8. Настройка CI/CD

Для автоматизации сборки и развёртывания используется GitHub Actions.

Настроен workflow `.github/workflows/ci.yml`.

### Этапы pipeline

| Этап | Содержание |
|---|---|
| Build and Test | Проверка форматирования, сборка, тестирование, отчёты |
| Publish Docker image | Сборка и публикация Docker-образа |
| Deploy and Verify | Запуск контейнеров и проверка работоспособности |

Для сборки Docker-образов поддерживаются архитектуры `linux/amd64` и `linux/arm64`.

Готовые образы публикуются в GitHub Container Registry с тегом, соответствующим SHA коммита.

Публикация и развёртывание выполняются после успешного завершения обязательных проверок.

Пароли передаются через механизм GitHub Actions Secrets.

### Проверка автоматического развёртывания

Развёртывание выполняется через Docker Compose на GitHub-hosted runner с Ubuntu.

После запуска выполняются проверки:

- `/actuator/health`;
- `/api/categories`.

Результаты выполнения сохраняются в логах и артефактах GitHub Actions.

Успешное выполнение pipeline подтверждает возможность автоматизированного запуска опубликованного приложения.

## 10. Ограничения решения

Реализованное приложение представляет собой единый серверный сервис без графического пользовательского интерфейса.

Автоматизированное развёртывание выполняется во временном окружении GitHub Actions. После завершения задания контейнеры останавливаются.

Постоянный сервер для непрерывного размещения приложения не используется.

Rollback проверен вручную на локальном стенде. Автоматическая процедура возврата предыдущего образа в pipeline не реализована.

Сквозные бизнес-сценарии автоматизированы на уровне MockMvc и тестовой базы PostgreSQL.
